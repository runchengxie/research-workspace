# 文档写作与维护约定

本工作区的说明文档以中文为主。文档首先服务于需要理解系统、运行命令或核对事实的人，
所以应优先说明结论、用途、入口和限制。

## 表达方式

- 使用短句和主动表达，先说明结论，再补充原因和操作方法。
- 使用准确的中文术语。首次出现的包名、命令、配置键、API 和数据字段保留行内代码。
- 删除没有信息价值的引导语、重复总结和抽象名词堆叠。
- 同一事实只保留一个权威入口，其他文档链接过去。
- 现状、计划、历史记录分开书写，并标明日期或状态来源。

## 标点与排版

- 中文正文使用全角逗号、句号、冒号、问号和括号。
- 英文命令、路径、文件名、配置和代码块保留原文标点。
- 少用双引号。需要强调术语时使用行内代码或直接说明。
- 少用加粗、分号和破折号。层次优先使用标题、列表和表格。
- 中英文相邻时保留必要空格，例如 `strategy-pipeline` 项目、`targets.json` 文件。

## 事实管理

- 动态数量、版本号、路径状态和测试结果应尽量来自脚本、测试、manifest 或 receipt。
- 根 README 只保留定位、快速开始、核心边界和文档入口。
- `docs/README.md` 只做导航，不复制动态状态表。
- `AGENTS.md` 记录协作规则、文件边界和验证要求，不承担产品说明。
- ADR、计划、证据和 archive 保存历史背景。修正历史记录时应保留原始事实和日期。
- 修改路径、命令、配置或输出契约时，同时检查代码、测试和相关文档。

## 目录与生命周期

文档按主要读者和维护责任归类。优先使用以下目录语义：

- `architecture/`：边界、设计、ADR 索引和稳定架构参考
- `concepts/`：当前概念、术语和方法说明
- `guides/`：面向读者的使用和接入指南
- `operations/`：安装、运行、检查、发布和故障处理
- `reference/`：API、配置、字段、产物和兼容性参考
- `research/`：当前研究问题、实验方法和结果入口
- `governance/`：质量、所有权、生命周期和维护规则
- `archive/`：历史记录、冻结材料和已结束迁移
- `evidence/`：带日期、哈希或机器生成的证据

入口文档使用短状态块：

```text
> status: active | reference | archived | superseded
> owner: <repository or workspace>
> audience: human | agent | both
> last_verified: YYYY-MM-DD
> source_of_truth: yes | no
> superseded_by: n/a | <relative path>
```

正文迁移后，旧路径保留兼容指针。指针只包含范围说明、当前链接和 `superseded` 状态，不复制原正文，不进入推荐阅读路径。

## AI 阅读顺序

编码代理默认按以下顺序读取文档：

1. 当前仓库根目录 `README.md`。
2. 当前仓库 `docs/README.md`。
3. 与任务直接相关的一个分类目录 README 和目标页面。
4. 任务明确涉及历史、证据、设计或实施计划时，再读取对应生命周期目录。

默认不递归读取全部 Markdown，也不把 `archive/`、`evidence/`、`superpowers/` 中的材料当作当前实现说明。

## 审阅清单

提交文档改动前检查：

1. 读者能否在开头找到用途和下一步入口。
2. 代码块中的命令、路径和配置是否仍然存在。
3. 是否把历史状态写成当前能力。
4. 是否混入了不必要的英文长句或翻译腔。
5. 是否有重复的否定转折、双引号、加粗、分号或破折号。
6. 相对链接是否都能解析。
